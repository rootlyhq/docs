RCA: Web chat offers most users only read-only tools, so it hands back incident-update, paging and retro asks that Slack completes, and the agent rarely links help-center docs, which leaves Tier 2 almost empty.

Unmitigated · sev4 · 3,155 users across 397 paying teams had an agent session in 90 days; 21,403 user messages on chat surfaces affected · Decision: accept — no action

Summary

The data pack for the homepage redesign is published as a purple, light and dark artifact: https://claude.ai/code/artifact/9347689e-bea8-4593-b86b-a62b70c88d40. Across 21,403 asks from paying teams in 90 days, the agent gave a final reply without refusing to 89.9% (Tier 1, an upper bound because there is no resolution feedback), pointed to docs for 0.78% (Tier 2) and handed back 9.3% (Tier 3). Web, where the homepage will live, hands back 27.5% of asks, mostly because web chat has no incident-update, paging or retro tools. Guardrails and the parity flag were checked and are not material causes. The proposed KR is at least 85% resolved, measured by a real resolution signal; Tier 2 used for config and admin questions; and at most 9% handed back on the homepage (Slack's level), with 5% as a stretch. Braintrust log data and homepage traffic by persona are still missing.

Impact

No outage: over 90 days the Rootly Agent gave paying teams a final reply without refusing to 90% of their asks, but handed 27.5% of web asks back to the user, against 8.8% in Slack.

Root cause

Web chat offers most users only read-only tools, so it hands back incident-update, paging and retro asks that Slack completes, and the agent rarely links help-center docs, which leaves Tier 2 almost empty.

Confidence: medium

Trigger

No incident trigger: the homepage redesign kickoff asked for data to size a 3-tier KR before the agent moves from the incident page to a global component.

Detection

Measured on request with text rules over ai_session_messages; there is no structured refusal tag or resolution feedback, so no dashboard tracks tier rates today.

Resolution

Data pack published; the KR targets and the web write-tool scope are product decisions still to make.

Signals

  • Answered (Tier 1 upper bound): 89.9% (19,242 of 21,403 asks; only 48 explicit corrections in 2,112 follow-ups)
  • Web handback (Tier 3): 27.5% (vs 8.8% in Slack and 2.4% on mobile)
  • Docs / self-serve (Tier 2): 0.78% (167 asks; the agent rarely links help-center docs)
  • Time to final reply, p50: 8.8s (p95 37s; web 8.5s, Slack 9.3s)

    • Chain of why

  • More than one in four web asks to the agent ends with the work handed back to the user.
  • Web chat refuses incident updates, paging and retros that Slack completes.
  • Web chat keeps only READ_ONLY_TOOLS unless the user passes home-chat gating, and even then it has no incident-update, paging or retro tool.
  • Write access on web was scoped to the early home-chat rollout and never extended to incident-level actions.
  • The scope of web write tools for the global agent is a product decision the homepage redesign has to make now.

    • What was tested

  • h1 [ruled out, medium confidence] Home chat refuses most action requests because app/services/ai/tools/home_write_allowlist.rb omits the write tools for declare incident, paging/escalation, status page, retrospectives, Slack channel actions and Jira, so the model has no tool to call and answers in plain text that it can't. — home_write_allowlist.rb static WRITE_TOOLS omit declare/page/status-page/retro/Slack/Jira, but HomeWriteAllowlist.tools adds `(parity_writes?(team) ? parity_write_tools : [])` where parity_write_tools = Registry.all.select(&:home_chat_write?); `home_chat_write` is declared in create_incident.rb:31, request_page.rb:61, create_status_page_announcement.rb:42, update_status_page_status.rb:77, update_incident.rb:31, update_incident_roles.rb:15, so declare/page/status page/update are available on home chat when flag enable_ai_assistant_required_fields_v2 is on. Only retros, Slack channel actions and Jira have no home_chat_write tool. Report (tmp/soil/report.html) shows home_chat had only 67 sessions across 2 teams in 90d vs 1,136 web incident-chat sessions across 226 teams, and home-chat refusals for available actions are only 2-13%, so the allowlist cannot account for most of the 268 refusals, which are attributed to web incident chat being read-only and Slack-native requests.
  • h2 [measured, medium confidence] Web incident chat refuses incident updates, paging and retros (33%/40%/60%) because that surface is deliberately read-only: write tools are filtered out of the surface's tool set (ai_allowed_tools / surface config) and the system prompt tells the model to say web is read-only. — app/services/ai/features/web_chat.rb#resolve_tools: `tools = Registry.for_context(**base).select { |tool| READ_ONLY_TOOLS.include?(tool.class) }`; write tools are added only `if @kwargs[:tool_access]&.to_sym == :home_write`. app/controllers/account/ai/chat/stream_controller.rb:36: `tool_access = :home_write if session.incident_chat? && home_write_enabled?`. home_write_enabled? calls HomeAiChatGating.enabled?, which requires user.theme == 'light_v2', the 'ai-native-home' flag and an IR or on-call seat. config/ai/prompts/web_chat.yml: 'Most users only have read-only tools: you can answer questions and look things up, but you cannot take mutating actions (paging, editing the incident, etc.). If the user asks for an action you have no tool for, say so plainly in one sentence'. HomeWriteAllowlist::WRITE_TOOLS contains no incident update, RequestPage or retro write tool, and parity_write_surface? limits incident-update parity writes to home_chat/dashboard_chat sessions. Differences from the hypothesis: the filter is the hardcoded READ_ONLY_TOOLS constant, not ai_allowed_tools; the read-only state is per user, not surface-wide; the prompt says 'most users only have read-only tools', not 'web is read-only'.
  • h3 [ruled out, medium confidence] Incident-update refusals (the top category, 34 teams) come mainly from the enable_ai_assistant_required_fields_v2 LaunchDarkly flag being off for most paying teams, which keeps the incident update tool out of the agent's tool set. — Re-investigated 2026-11-12 in Metabase Main DB. flipper_gates for enable_ai_assistant_required_fields_v2 has only 9 'actors' rows and no boolean, group or percentage gate, so the flag is off for almost every paying team. But the flag only scopes home/dashboard chat, and those surfaces carry almost no volume (home chat ~67 sessions, 2 teams). Of 1,994 handed-back asks in 90 days, 1,472 are on Slack and 432 on web incident chat, where the flag does not gate UpdateIncident. The flag being off is real but cannot explain the refusals measured.   • h5 [ruled out, medium confidence] Some refusals are false 'can't do that' replies from the guardrails in config/ai/guardrails.yml (off-topic and empty-context rules) firing on legitimate action requests, so the agent declines even when a matching tool is available on that surface. — Re-investigated 2026-11-12 in Metabase Main DB (paying teams, 90d, chat surfaces).     • Lessons learned

    Went well

  • Main DB had enough to size every tier, split by surface, cluster intents, check the PRD's prompts and rank manual actions.
  • Checking the shape of assistant messages caught that 70% are tool-call rows, which corrected Tier 3 from 5.3% to 9.3% before the numbers reached the PRD.

    • Went wrong

  • The lane first narrowed to refusals and delivered no artifact, then shipped tier numbers that paired asks with tool-call rows; both needed rework.
  • Braintrust log reads stayed blocked by the hook, so no trace-level data is in the artifact.
  • Feedback is empty, so Tier 1 is only an upper bound.

    • Got lucky

  • Home chat has almost no volume yet (about 67 sessions), so the web read-only gap has not hit homepage users at scale.
  • If the 90-day window had covered only Sep 21 to Oct 11, Tier 3 would have read about 4% and the KR target would have been set too low.

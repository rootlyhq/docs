What this means for the homepage

  • Declare, update/resolve, page and retro are the gaps that matter for a web launchpad. Refusal rates are low in Slack but high in web chat: 33% for incident updates, 40% for paging, 60% for retros. Today's web incident chat runs mostly read-only. Most web refusals give "I'm read-only here" as the reason (98 sessions, 50 teams).
  • Home chat already gets more write tools than incident chat. These are action items, timeline events, alert ack/resolve/snooze/escalate, automations and investigations, plus flag-gated workflows, schedule edits, invites and shift overrides (app/services/ai/tools/home_write_allowlist.rb). Asks for those actions are refused rarely, about 2–13%. Home chat has no tool to declare an incident, page someone, post a status page update, write retros, act on Slack channels or create Jira tickets. Incident updates are available only behind the enable_ai_assistant_required_fields_v2 parity flag.
  • Channel and bridge actions (#2) and posting messages (#3) are Slack-native requests. They matter less for the homepage, but they are the most common "no tool exists" refusals overall.
  • There is no home-chat baseline yet. Web home_chat sessions: 67 in 90 days, across 2 teams. Web incident chat (web_chat on an Incident): 1,136 sessions across 226 teams.

Method

  • Unit: each user message in ai_session_messages, paired with the next assistant reply in the same session. Teams: paying_customer, not sandbox, not deleted. Matches the existing "Rootly Agent adoption funnel" card.
  • Action type: keyword and regex buckets on the user message. Only messages that request an action are counted. Questions and lookups are excluded.
  • Refused: the reply contains can't-do wording ("I can't / don't have a tool / don't have the ability / read-only / outside what I…"). Replies that are data misses ("can't find / see / access / confirm") are excluded.
  • Precision check: I read a random sample of 50 flagged pairs. About 41 were real refusals of an action. The misreads were data-access replies, summary-quality caveats and an off-topic grammar request. No customer text is reproduced here.
  • Counts are lower bounds. Recall was not measured: messages in other languages, unusual phrasing and multi-turn refusals are missed.

Data gaps

Braintrust: blocked. sql_query and infer_schema were refused by the lane's read-only hook ("this automation lets it read only"). Only listing projects worked. No numbers from Braintrust spans are included, and none were estimated. Per the code, production chat turns log to project rootly as ai.<feature> spans. Denials carry only a tool_error_type metadata key, and there is no refusal scorer.
Metabase: available in this lane, unlike in the operator session. All numbers above come from it (Main DB, id 2).
No structured refusal tag exists. The guardrail refusals and "no tool for that" replies are plain assistant text (config/ai/guardrails.yml). That's why the ranking relies on text classification. To track this going forward, tag those turns or add a Braintrust scorer.
ai_tool_call_events starts 2026-10-29, so tool-level denials cover only about 2 weeks.
Not queried: Datadog [Ai::CapabilityMissing] logs. They cover "agent disabled" and failed turns, not action refusals. Which tool each checkpoint was for is also unavailable: ai_pending_checkpoints has no tool column.
Scope differences: the 23.7k session total, the per-reason splits in the first refusal pass, and the checkpoint counts include all teams, internal and QA included. The ranked table and the reason splits above are limited to paying teams.
